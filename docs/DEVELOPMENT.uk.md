# Локальна розробка Tanuki Shop

## Підготовка

Використовуйте Node.js 24 і npm. Версія Wrangler зафіксована в `package.json`. Перше встановлення:

```bash
node --version
npm install
cp .dev.vars.example .dev.vars
```

У поточному середовищі мережеве встановлення не завершилося. Тому lockfile, Wrangler dry-run, генерація типів і запуск local D1/R2 ще не підтверджені. Після успішного встановлення потрібно перевірити ці команди та додати згенерований `package-lock.json`; надалі використовувати `npm ci`. Локальні Node-перевірки `npm run check` і `npm test` не потребують встановлення пакетів.

Перед запуском адмінпанелі задайте у `.dev.vars` окремий пароль для локальної розробки. Не копіюйте production-паролі чи токени в тестові дані, SQL або вихідний код. Файл із локальними секретами виключений із Git.

Для каталогу та тестового оформлення Telegram не обов’язковий: без його секретів Worker не надсилає сповіщення. Для перевірки фактичної доставки згодом потрібні окремий тестовий бот і тестовий чат.

## База даних і демонстраційний каталог

```bash
npm run db:local:init
npm run db:local:seed
```

Команди використовують `wrangler.local.jsonc` і локальний режим D1. Схема `dev/schema.sql` відтворює таблиці, потрібні наявним API, для розробки та тестів. `dev/seed.sql` додає демонстраційні товари. Їх можна застосовувати повторно: створення таблиць і додавання демонстраційних записів не повинні дублювати дані.

Ці файли не є експортом production, baseline або міграціями існуючої БД. Фактична схема `tanuki-shop-db` ще потребує read-only звірки. Не застосовуйте локальну fixture до production. Перед майбутніми міграціями потрібно зафіксувати реальну схему й перевірити відновлення без видалення наявних користувачів та замовлень.

Локальний стан Wrangler зберігається в `.wrangler/` і не комітиться. У ньому можуть залишатися замовлення та зображення між запусками. Для звичайного запуску очищати його не потрібно.

## Запуск

```bash
npm run dev
```

Використовується локальна конфігурація з окремими назвами D1/R2 і `remote: false`. Файл `wrangler.jsonc` продовжує описувати наявний production Worker та його bindings. Команда локальної розробки не виконує deploy.

Локальний сервер слухає `http://127.0.0.1:8787`. Корисні маршрути:

| Маршрут | Призначення |
|---|---|
| `/` | Вітрина й кошик |
| `/admin/` | Адмінпанель; вхід за локальним паролем |
| `/api/health` | Перевірка з’єднання з поточною локальною D1 |
| `/api/products` | Каталог із поточної локальної D1 |
| `/media/*` | Видача фотографій із поточного локального R2 |

Фотографії, додані через локальну адмінпанель, зберігаються локально. У демонстраційних товарів може не бути фотографій.

Вітрина зберігає наявний зовнішній чат-віджет KeyCRM. Поки немає окремої тестової конфігурації віджета, повідомлення через нього не входять до ізольованих локальних перевірок.

## Перевірки перед змінами

```bash
npm run check
npm test
npm run build:check
```

`check` запускає статичні перевірки, визначені в `package.json`. `test` використовує Node test runner і SQLite-адаптер D1 у пам’яті. Кожен тест працює зі своїми тестовими даними; production credentials не використовуються. Зовнішні HTTP-виклики в цих тестах заблоковані.

Тести перевіряють логіку наявного Worker: серверні ціни, позиції замовлень, залишки, доступ до admin API та webhook. Це не Miniflare/workerd і не перевірка поведінки Cloudflare під розподіленим навантаженням. Позначки `todo` описують відомі прогалини; їх не можна трактувати як успішне виправлення.

`build:check` виконує Wrangler dry-run із локальною конфігурацією без публікації Worker. Успішна збірка не підтверджує DNS, стан production bindings, доступність бази, надсилання email/Telegram або роботу сторінок у браузері.

Після зміни локальних bindings можна оновити згенеровані типи:

```bash
npm run types
```

Згенеровані файли розміщуються в `.wrangler/` і не комітяться.

Для перевірки інтерфейсу запустіть локальний сервер і пройдіть каталог → кошик → checkout та admin → товари/фото → замовлення. До реалізації авторизації покупця checkout лишається гостьовим. Усі створені тут дані мають бути демонстраційними.

## Production і наступні міграції

У цьому етапі немає команди, що застосовує remote-міграції, очищує production БД або публікує сайт. Перед наступним випуском потрібно:

1. Звірити фактичні Cloudflare bindings, домен, deployment і схему D1.
2. Перевірити backup/відновлення та зберегти порядок відкату.
3. Підготувати лише сумісні додавальні міграції й перевірити їх на окремому staging.
4. З’ясувати, які гілки запускають Cloudflare Builds, перш ніж пушити зміни.
5. Виконати integration/e2e та перевірити випуск на домені.

Нові customer-акаунти мають доповнювати наявні дані. Історичні замовлення й Telegram-зв’язки не потрібно видаляти або автоматично присвоювати за непідтвердженим телефоном/email.
